Über dieses Framework
Dieses Dokument basiert auf über einem Jahr praktischer Arbeit mit
KI-gestützter Entwicklung. Hunderte Stunden im Cursor Agent Mode,
dutzende Features produktiv ausgeliefert. Die dokumentierten Patterns
entstanden aus konkreten Fehlern und deren systematischer Analyse.
Das Framework zeigt, wie sich ChatGPT, Claude und Cursor professionell
in bestehende Entwicklungsprozesse integrieren lassen - ohne
Qualitätsverlust und mit nachweisbarem ROI.
Charakter dieses Frameworks
Praxisorientiert: Alle Inhalte stammen aus produktiver Anwendung.
Ehrlich: Dokumentiert wird, was funktioniert und was nicht.
Anwendbar: Sämtliche Prompts sind kopierbar, alle Übungen durchführbar.
Offen: Die Methodik ist adaptierbar für individuelle Arbeitsweisen.
Abgrenzung
Dieses Framework ist kein Prompt-Engineering-Guide, keine Tool-Dokumentation
und kein Manifest über die Zukunft der Entwicklung.
Es ist eine Arbeitsmethodik.
Zielgruppe
Das Framework richtet sich an Entwickler mit mindestens zwei
Jahren Berufserfahrung, die KI produktiv einsetzen wollen. Voraussetzung ist die
Bereitschaft, etablierte Arbeitsweisen kritisch zu hinterfragen.
Nicht geeignet für Programmier-Anfänger, Personen ohne technischen Hintergrund
oder Leser, die fertige Copy-Paste-Lösungen erwarten.
Hinweise zur Nutzung
1. Teil I (Foundations) vollständig lesen
2. Die drei Übungen aus Teil III parallel zu Teil II bearbeiten
3. Teil IV (Resources) als Nachschlagewerk verwenden
4. Die .cursorrules für eigene Projekte adaptieren
Hinweis für Teams: Die .cursorrules lassen sich im Team teilen und schaffen so eine
konsistente Code-Qualität über alle Beteiligten.
Was ist PULSE?
PULSE beschreibt eine Arbeitsweise, bei der KI-Systeme autonom in Loops laufen -
und du nur an den entscheidenden Punkten steuerst.
Ein Pulse ist immer ein präziser Eingriff:
• Start-Pulse (Prompt oder Kontext, der einen Loop startet)
• Korrektur-Pulse (Eingriff bei Abweichungen)
• Review-Pulse (Validierung, Quality Gate)
Der Loop läuft. Du setzt die Pulse. Das System bleibt unter Kontrolle.
Die Kapitel dieses Frameworks zeigen dir:
• Wo Pulse entstehen (Foundations)
• Wie du Pulse formulierst (6-Elemente)
• Welche Patterns funktionieren (Workflow-Patterns)
• Wann Pulse nötig sind (Safety & Eskalation)
• Wie du fehlerhafte Loops unterbrichst (Debug)
• Wie du mehrere Loops parallel steuerst (Parallel Work)
Warum "PULSE"?
Dein Herzschlag läuft kontinuierlich - aber ohne die rhythmischen Spitzen würde
das Blut nicht zirkulieren. Der Pulse ist der Moment, wo Energie ins System
gedrückt wird.
Genauso bei KI-gestützter Entwicklung: Der Loop läuft autonom. Aber ohne deine
gezielten Eingriffe verliert er Richtung und Kraft. Jeder Pulse schiebt neue Energie
rein - einen Kontext-Reset, eine Korrektur, eine Qualitätsprüfung.
Nicht konstante Überwachung. Sondern rhythmische Kontrolle.

TEIL I: FOUNDATIONS
Dein technisches Setup
Bevor du auch nur einen Prompt schreibst: Dein Setup entscheidet über Erfolg oder
Scheitern. Die meisten Entwickler scheitern nicht an schlechten Prompts, sondern
an fehlendem System.
1. Die 3-Ebenen-Architektur
KI-gestützte Entwicklung ist kein Single-Tool-Job. Du brauchst eine Architektur, in
der jedes Tool seine spezifische Rolle hat.
Ebene 1: Konzept & Strategie (ChatGPT/Claude)
Zweck: Denken, nicht Bauen
Was hier passiert:
• Anforderungen verstehen und strukturieren
• Architektur-Entscheidungen diskutieren
• Technische Konzepte als .md-Dateien erstellen
• Komplexe Probleme in lösbare Schritte zerlegen
Warum nicht direkt in Cursor starten?
Cursor ist ein Bauarbeiter. Wenn du ihm sagst "Bau mir was Schönes", baut er. Aber
ohne Bauplan wird's Murks.
Faustregel: Je größer das Feature, desto mehr Zeit in ChatGPT/Claude VOR Cursor.
Praktisches Setup:
ChatGPT Projects / Claude Projects:
• Ein Haupt-Project pro Arbeitskontext - z.B. "RSLT AI Development"
• Hinterlege Kontext-Dateien - Brand Guidelines, Tech Stack, Coding Standards
• NICHT ein Project pro Kunde - Das wird unübersichtlich
• Jeden Chat neu starten - Vermeidet Bias aus vorherigen Gesprächen
Ebene 2: Build & Implementierung (Cursor)
Zweck: Konzept in funktionierenden Code umsetzen
Was hier passiert:
• Konzept-Datei (.md) als Grundlage laden
• Composer + Agent Mode für Multi-File-Edits
• Kontinuierliche Git-Commits (alle 5-10 Min)
• Selbstständiges Testing im Browser (wo möglich)

Ebene 3: Eskalation & Problemlösung
Zweck: Wenn Cursor hängt, brauchst du eine zweite Meinung
Wann eskalieren?
• Cursor macht 2-3x denselben Fehler (Loop detected)
• Cursor sagt "ist gefixt" aber offensichtlich nicht
• Cursor versteht dein Problem nicht, auch nach Umformulierung
• Lösung fühlt sich architektonisch falsch an
Der Eskalations-Workflow:
Schritt 1: Cursor fragen
"Erkläre mir unser aktuelles Problem so, dass ich es einem anderen Entwickler
erklären kann. Beschreibe: IST-Zustand, SOLL-Zustand, was wir versucht haben,
warum es nicht funktioniert."
Schritt 2: Problem exportieren
Entweder Cursor's Erklärung kopieren ODER Projekt-Export-Script nutzen:
"Erstelle ein Script, das alle projekt-relevanten Code-Dateien in eine Text-Datei
mit absoluten Pfad-Angaben schreibt."
Schritt 3: An ChatGPT/Claude als "externen Dev"
"Du bist ein Senior Developer, der sich ein bestehendes Projekt anschaut. Hier ist
der aktuelle Stand [Export], hier ist das Problem [Cursor's Erklärung]. Gib mir eine
Lösung, die ich meinem Entwickler (Cursor) als Anweisung geben kann."
Schritt 4: Lösung zurück zu Cursor
ChatGPT's Lösung als Anweisung an Cursor geben - nicht Copy-Paste von Code,
sondern die Idee/Strategie.
Warum dieser Umweg?
Weil Cursor im Projekt-Kontext feststeckt. Ein frischer Blick (ChatGPT/Claude ohne
Project-History) sieht das Problem oft anders. Du bist der Übersetzer zwischen
beiden.

3. Git als Sicherheitsnetz & Denk-Werkzeug
Git ist nicht optional. Ohne Git ist Agent Mode russisches Roulette.
Der Git-Workflow:
1. Projekt-Start: Sofort Git-Repo anlegen
git init
git add .
git commit -m "Initial commit"
2. Während Agent Mode läuft: Alle 5-10 Min Checkpoint
Nicht manuell - Cursor macht das automatisch, wenn du es richtig konfigurierst.
Aber du solltest Git-Log im Blick haben.
3. Nach jedem Feature: Aussagekräftiger Commit
feat: add user authentication with JWT
- Added JWT token generation and validation
- Implemented refresh token mechanism
- Added middleware for protected routes
- Tests for all auth flows
Closes #123
Warum so ausführliche Commits?
• Cherry-Picking: Du willst später einzelne Features in andere Projekte
übertragen
• Debugging: "Wann haben wir das geändert und warum?"
• Dokumentation: Git-History ist durchsuchbare Wissensdatenbank
• Onboarding: Neue Team-Mitglieder lesen Git-Log um Projekt zu verstehen
Sprache in Commits:
IMMER Englisch. Auch wenn dein Code auf Deutsch kommentiert ist. Warum? Weil
du international arbeiten wirst, deine Tools international sind, und englische
Commits in Stack Overflow, GitHub, etc. besser durchsuchbar sind, auch für die KI.
4. Das Dokumentations-System
Code alleine ist keine Dokumentation. Du brauchst ein System, das während der
Arbeit wächst - nicht am Ende als Pflichtübung.
3-Ebenen-Dokumentation:
Ebene 1: .cursorrules (Projekt-spezifische Regeln)
Location: Im Root jedes Projekts
Inhalt:
• README-Content (Projekt-Übersicht, Setup-Anleitung)
• API-Dokumentation (Endpoints, Parameter, Responses)
• Deployment-Infos (Wie deployed man, wo sind Secrets)
• Wiederkehrende Probleme & Lösungen ("Wenn X passiert, mach Y")
Warum in .cursorrules? Weil du sie beim Prompten per @ referenzieren kannst.
Cursor liest sie automatisch bei kritischen Operationen.
Ebene 2: /docs/ (Feature-Dokumentation)
Location: /docs/ Ordner im Root
Naming-Convention:
docs/
2025-11-12_payment-integration-problem.md
2025-11-10_auth-flow-redesign.md
2025-11-08_database-migration-learnings.md
Inhalt pro Datei:
• Problem-Beschreibung (Was war kaputt/unklar)
• Lösungs-Ansätze (Was haben wir versucht)
• Finale Lösung (Was hat funktioniert)
• Learnings (Was nehmen wir mit)
Ebene 3: Globale Cursor Rules
Location: Einstellungen -> User Rules (gilt für ALLE Projekte)
Inhalt:
• System-Info (Mac M2, Node Version, Python Version)
• Generelle Coding-Standards (Formatting, Naming)
• Sicherheits-Regeln (Nie Secrets committen, etc.)
• Übergreifende Best Practices
Wer schreibt die Dokumentation?
Die KI. Immer.
Wenn ein Problem gelöst wurde:
"Dokumentiere dieses Problem und die Lösung in einer .md-Datei. Dateiname:
docs/[DATUM]_[KURZBESCHREIBUNG].md. Struktur: Problem, Lösungsansätze,
Finale Lösung, Learnings."
Wenn ein Problem wiederholt auftritt:
"Füge diese Erkenntnis den .cursorrules hinzu, damit wir beim nächsten Mal
automatisch richtig vorgehen."
Das Prinzip: Selbstlernendes System
Jedes Problem, das du löst, macht dein Projekt intelligenter. Die .cursorrules
werden zum institutionellen Gedächtnis. Neue Entwickler (oder KI-Agents)
profitieren automatisch von allem, was vorher gelernt wurde.
Zusammenfassung: Deine Setup-Checklist
Bevor du mit einem neuen Projekt startest:
✅ ChatGPT/Claude Project angelegt mit Kontext-Dateien
✅ Git-Repo initialisiert
✅ .cursorrules Datei erstellt (kopiere Template aus Teil IV)
✅ /docs/ Ordner angelegt

TEIL II: DAS 6-ELEMENTE-FRAMEWORK
Wie du Prompts schreibst, die funktionieren
Die meisten Entwickler scheitern nicht an der KI. Sie scheitern an ihren Prompts.
"Bau mir eine Login-Form" → KI baut irgendwas
"Das ist falsch" → KI ändert irgendwas
"Immer noch falsch" → "KI funktioniert nicht"
Problem: Nicht die KI, sondern fehlender Kontext.
Die 6 Elemente eines funktionierenden Prompts
Jeder gute Prompt besteht aus maximal 6 Elementen. Nicht alle sind immer nötig -
aber Minimum 3-4 sollten dabei sein.
Element 1: ROLLE
Was ist das?
Du sagst der KI explizit, aus welcher Perspektive sie arbeiten soll. Nicht "du bist ein
AI", sondern eine konkrete professionelle Rolle.
Beispiele:
❌ Schlecht: "Hilf mir mit diesem Code"
✅ Gut: "Du bist ein Senior Backend Developer mit 10 Jahren Node.js-Erfahrung"
✅ Besser: "Du bist ein Senior Backend Developer, der dieses Projekt von Anfang
an betreut hat und es besser kennt als jeder andere"

LLMs sind Pattern-Matcher. "Senior Developer" aktiviert andere Patterns als "AI
Assistant". Die Rolle gibt der KI einen Kontext, aus dem sie Entscheidungen trifft.

Die 3 größten Anfänger-Fehler beim Prompten
Fehler 1: Ungeduld + "In Stein gemeißelt"
Das Problem:
Entwickler schreiben einen Prompt, KI gibt Antwort, Antwort ist nicht perfekt → "KI
funktioniert nicht für mich"
Die Realität:
Kein Prompt ist perfekt beim ersten Mal. Das erste Ergebnis ist ein VORSCHLAG,
keine Wahrheit. Du musst iterieren.
Richtig machen:
Prompt 1: "Versteh das erstmal" → [KI erklärt]
Prompt 2: "Gut, jetzt entwickeln wir das Konzept Schritt für Schritt"
Prompt 3: "Das Konzept sieht gut aus, lass uns mit der Implementierung starten"
Prompt 4: "Der Login-Flow fehlt noch, ergänze das"
Prompt 5: "Jetzt fügen wir Error-Handling hinzu"
→ 5 Prompts, aber jedes Zwischenergebnis wird besser
Fehler 2: Zu vage + zu viel vorausgesetzt
Das Problem:
"Bau mir eine API" → KI weiß nicht: Welcher Stack? Welche Authentifizierung?
Welches Datenbank-Schema? REST oder GraphQL?
Die Realität:
Die KI kann nicht in deinen Kopf schauen. Was für dich "offensichtlich" ist ("natürlich
meine ich Next.js API Routes"), ist für die KI nicht offensichtlich.
Richtig machen:
Sag ALLES explizit. Auch wenn es dir redundant vorkommt. Die KI braucht:
• Tech Stack ("Next.js 14, TypeScript, Prisma, PostgreSQL")
• Konventionen ("Wir nutzen Server Actions, nicht API Routes")
• Dein Setup ("Mac M2, Node 20, Docker für DB")
• Bestehender Code ("Hier ist unsere Auth-Implementierung als Referenz")
• Coding-Standards ("TypeScript strict mode, ESLint, Prettier")
Fehler 3: An eigenen Maßstäben festhalten
Das Problem:
"So hab ich das noch nie gemacht" → Developer lehnt KI-Lösung ab, weil sie anders
ist als gewohnt.
Die Realität:
KI denkt anders als Menschen. Manchmal findet sie bessere Lösungen, die du nicht
gesehen hättest. Manchmal macht sie es nur anders, aber nicht schlechter.
Richtig machen:
• Frag dich: "Ist das objektiv schlechter, oder nur anders?"
• Wenn funktional korrekt: Akzeptiere den anderen Ansatz
• Wenn wirklich schlechter: Erkläre WARUMit schlechter ist (nicht nur "mach's so
wie ich")
• Nutze Beispiele um deinen Standard zu zeigen, aber sei offen für Alternativen
Das iterative Prinzip: Gemeinsam entwickeln
Die wichtigste Erkenntnis aus 1 Jahr KI-gestützter Entwicklung:
KI ist kein Automat, sondern Denkpartner.
Das bedeutet: Du gibst nicht einen perfekten Prompt und bekommst ein perfektes
Ergebnis. Du entwickelst die Lösung GEMEINSAM mit der KI, Schritt für Schritt.
Der ideale Entwicklungs-Flow:
Phase 1: Verstehen
Du: "Hier ist die Anforderung [Input]. Versteh das erstmal und erkläre mir, wie du
das umsetzen würdest."
KI: [Erklärt Verständnis und Ansatz]
Du: "Gut verstanden. Aber Punkt 3 würde ich anders machen, weil XY. Was hältst
du davon?"
KI: [Adjustiert Ansatz]
Phase 2: Konzept entwickeln
Du: "Jetzt entwickeln wir das technische Konzept. Schritt für Schritt, nicht alles
auf einmal. Starte mit der Datenbank-Struktur."
KI: [Zeigt DB-Schema]
Du: "Fast gut. User-Table fehlt noch das 'role' Feld. Ergänze das."
KI: [Updated Schema]
Du: "Perfekt. Jetzt die API-Struktur."
KI: [Zeigt API-Konzept]
Du: "Gut. Jetzt Frontend-Komponenten."
[...weitere Iterationen...]
Phase 3: Implementation
Du: "Konzept steht. Speichere das als concept.md. Dann starten wir die
Implementierung in Cursor."
[Wechsel zu Cursor]
Du: "Hier ist das Konzept [concept.md]. Implementiere Milestone 1: Datenbank-
Setup."
Cursor: [Baut DB-Schema, Migrations, Seed-Data]
Du: "Gut. Teste das selbstständig."
Cursor: [Testet, findet Issue]
Du: "Fixe das Issue und dann weiter zu Milestone 2."
[...weitere Milestones...]
Warum dieser Flow funktioniert:
• Du behältst Kontrolle (jeder Schritt wird validiert)
• KI bleibt fokussiert (nicht überfordert mit zu viel auf einmal)
• Du verstehst den Code (weil du jeden Schritt mitentwickelt hast)
• Fehler werden früh erkannt (nicht erst am Ende)
• Qualität bleibt hoch (iterative Verbesserung)

TEIL III: WORKFLOW-PATTERNS
Echte Prompts aus der Praxis
Theorie ist schön. Praxis ist besser. Hier sind echte Prompts aus echten Projekten -
ungefiltert, wie sie wirklich geschrieben wurden. Plus abgeleitete Beispiele im
gleichen Stil.
1. Feature-Erweiterung
Wenn du ein bestehendes Feature erweitern willst, ist der Kontext entscheidend.
Die KI muss verstehen: Was ist da, was fehlt, warum fehlt es.
Echtes Beispiel: Übungs-Auswahl erweitern
Kontext: User hat eine Meditation-App. Die Übungsauswahl basiert bisher nur auf
Stimmung. Soll erweitert werden um Zeitbudget.

nicht nur auf der Stimmung, sondern auch auf dem Zeitbudget basiert, damit
der User keine langen Übungen bekommt, wenn er wenig Zeit hat.
Was macht diesen Prompt gut?
• Klares Ziel: "erweiterte Version"
• Spezifische Ergänzung: "auch auf dem Zeitbudget basiert"
• User-Need: "damit der User keine langen Übungen bekommt"
• Implizite Logik: Kurz auf Zeit = nur kurze Übungen

3. Fallback wenn keine passende Übung (nächst-kürzere vorschlagen)
[ACTION]
interne Logik.
Erweitere den bestehenden Code. Ändere die Funktion-Signatur nicht, nur die

2. Analyse & Dokumentation
Wenn du willst, dass die KI ein Projekt versteht und dokumentiert, musst du ihr eine
Rolle geben und klare Output-Struktur vorgeben.
Echtes Beispiel: Projekt-Delta-Analyse
Kontext: Kunde hat Lastenheft für Phase 2. Du willst wissen: Was ist implementiert,
was fehlt.
Original-Prompt:
nochmal. hier Lastenheft Phase 2.pdf im root ist das dokument, in dem drin steht,
was der kunde noch vorhat. gehe das gesamte projekt durch, schau, was wir
schon haben und was noch nicht und schreibe das in eine neue datei, mit
genauen angaben, was da ist, was noch nicht aufgrund seines lastenhefts.
erstmal ohne zeitschätzungen, die machen wir separat. aber das dokument
muss so umfangreich und genau sein, wie nur möglich, du machst das in deiner
rolle des senior devs, der das projekt von anfang an betreut hat und besser kennt
als jeder andere.
Was macht diesen Prompt effektiv?
• "nochmal": Signalisiert: Vorheriger Versuch war nicht gut genug

TEIL IV: PEAK DETECTION & ESKALATION
Agent Mode unter Kontrolle
Agent Mode ist kein Autopilot. Es ist ein leistungsstarker Mitarbeiter, der Aufsicht
braucht.
In diesem Kapitel: Wie du Agent Mode produktiv nutzt, ohne dass er Chaos
anrichtet. Basierend auf echten Disasters und wie man sie verhindert.
1. Die 30-Minuten-Regel
Die wichtigste Regel aus 1 Jahr Agent-Mode-Erfahrung:
Niemals Agent Mode länger als 30 Minuten unbeaufsichtigt
lassen.
Warum genau 30 Minuten?
Erfahrungswert: Nach 30 Min ohne Aufsicht ist die Wahrscheinlichkeit hoch, dass
du alles rejecten und neu starten musst.
Was passiert nach 30 Minuten:
• Agent verliert Kontext (macht Änderungen die nicht zum ursprünglichen Ziel
passen)
• Baut in falsche Richtung (Feature-Creep ohne dass du es bemerkst)
• Macht zu viele Changes auf einmal (Debugging wird unmöglich)
• Überschreibt funktionierende Sachen ("Ich mach das mal besser")
• Erstellt Dependencies die du nicht willst (installiert random Packages)
Praktische Umsetzung:
Bei Projekt-Start mit Konzept-Datei:
• Agent Mode starten mit Konzept als Input
• 30-Minuten-Timer stellen
• Zuschauen was der Agent macht (nicht weggehen!)
• Verstehen: WAS er macht, WARUM er es so macht
• Nach 30 Min: Checkpoint, Review, neu starten oder weiter
Während Feature-Build:
• Alle 5-10 Min: Git-Commit (automatisch oder manuell)
• Kontinuierlich mitlesen was Agent macht
• Bei ersten Anzeichen von Loop oder falscher Richtung: Stop
• Maximal 30 Min bis nächster manueller Review
Hinweis: 30 Minuten autonome Runs sind eher selten, das soll wirklich nur als
potentielles Maximum an Autarkie für den Agent verstanden werden. Die meisten
autonomen Agent-Runs sind wesentlich kürzer.
2. Safeguards: Was der Agent NICHT darf
Agent Mode braucht klare Grenzen. Diese Regeln sind non-negotiable.
Die 5 Critical Safeguards:
1. DELETE nur nach Nachfrage
Agent darf Dateien löschen NICHT eigenständig entscheiden. Jeder DELETE muss
explizit bestätigt werden.
In .cursorrules:
RULE: File Deletion
NEVER delete files without explicit confirmation.
ALWAYS ask: "Should I delete [filename]? This cannot be undone."
WAIT for user confirmation before proceeding.
Die „Nicht selbständig löschen“ Angabe wird auch in den Cursor Einstellungen als
fester Parameter gesetzt, der Zusatz in den .cursorrules gilt nur als doppelte
Absicherung.
2. GIT PUSH nur nach Nachfrage
Agent darf committen (das ist OK), aber NICHT pushen ohne Erlaubnis. Du willst
Review-Möglichkeit bevor es remote ist.
In .cursorrules:
RULE: Git Push
NEVER push to remote without explicit permission.
Local commits: OK
Remote push: ALWAYS ask first
Exception: When explicitly told "push this"
Der „GIT PUSH“ Befehl darf explizit nicht bei den erlaubten Commands hinterlegt
sein. Die Information in der .cursorrules Datei gilt nur als doppelte Absicherung.
3. ERST lokal testen, DANN deployen
Agent soll NIEMALS direkt auf Production deployen. Immer erst lokal validieren.
In .cursorrules:
RULE: Deployment
Testing Pipeline: Local → Test → Staging → Production
NEVER skip testing steps
NEVER deploy directly to production
ALWAYS test locally first using npm run dev or similar
4. KEINE breaking Changes ohne Warning
Wenn Agent merkt "das wird Breaking sein", muss er warnen BEVOR er es macht.
In .cursorrules:
RULE: Breaking Changes
Before making changes that break existing functionality:
1. Identify impact (which components/features affected)
2. Warn user: "This will break [X]. Proceed?"
3. Wait for confirmation
Examples: API signature changes, DB schema changes, prop renames
5. KEINE Secrets im Code
Agent darf NIEMALS API-Keys, Passwords, Tokens direkt in Code schreiben.
In .cursorrules:
RULE: Secrets Management
NEVER hardcode:
- API Keys
- Passwords
- Access Tokens
- Database URLs
ALWAYS use:
- Environment variables (process.env.XYZ)
- .env files (not committed)
- Secret management services
If you need a secret: Ask user to add to .env
3. Loop Detection: Wann eskalieren?
Loops sind das häufigste Problem mit Agent Mode. Du musst lernen, sie schnell zu
erkennen.
Die 4 häufigsten Loop-Typen:
Loop-Typ 1: "Ist gefixt" aber offensichtlich nicht
Agent macht Change, sagt "Problem gelöst", aber du siehst: Problem existiert noch.
Erkennung:
• Agent committed "fix: [problem]"
• Du testest: Problem ist noch da
• Agent macht wieder Change: "fix: [same problem]"
• Du testest: Immer noch nicht gefixt
Action nach 2-3 Iterationen:
1. STOP Agent Mode
2. Reject letzte 2-3 Commits
3. Eskaliere zu ChatGPT/Claude:
"Cursor hat 3x versucht [Problem] zu fixen, hat aber nicht funktioniert. Hier ist der
Code [paste], hier ist der Error [paste]. Gib mir eine Lösung die ich Cursor als
Anweisung geben kann."
Loop-Typ 2: Hin-und-Her zwischen 2 Lösungen
Agent macht Change A, dann zurück zu Change B, dann wieder A...
Erkennung:
• Commit 1: "use approach X"
• Commit 2: "revert to approach Y"
• Commit 3: "actually X is better"
• Git-Diff zeigt: Immer dieselben Zeilen geändert
Action sofort:
1. STOP Agent Mode
2. Git Reset zu letztem stabilen Stand
3. Klare Entscheidung treffen (du oder mit ChatGPT)
4. Agent mit EXPLIZITER Anweisung neu starten:
"Nutze Approach X. NICHT Approach Y. Hier ist warum: [Begründung]"
Loop-Typ 3: Versteht Problem nicht
Du beschreibst Problem, Agent macht irgendwas, aber offensichtlich hat er nicht
verstanden.
Erkennung:
• Agent macht Changes an falschen Dateien
• Agent fixiert völlig anderes Problem
• Du wiederholst Anweisung 2-3x, Agent macht trotzdem was anderes
Action sofort:
1. STOP Agent Mode
2. Wechsel zu Chat (nicht Composer)
3. Frag Agent: "Erkläre mir, was du verstanden hast. Was ist das Problem, was
versuchst du zu lösen?"
4. Wenn Erklärung falsch: Korrigiere Verständnis BEVOR du weiter machst
5. Erst wenn Agent korrekt erklärt: Zurück zu Composer
Loop-Typ 4: Macht zu viel auf einmal
Agent macht 20 Changes gleichzeitig, etwas geht kaputt, du weißt nicht was.
Erkennung:
• Ein Commit ändert 15+ Dateien
• Mix aus Feature-Arbeit + Refactoring + Bug-Fixes
• Du kannst nicht nachvollziehen was kaputt gegangen ist
Prevention (besser als Cure):
Gib Agent kleinere Milestones:
❌ Schlecht:
"Bau das komplette User-Management-Feature"
✅ Gut:
"Milestone 1: Nur das User-Model und Prisma-Migration"
[Agent macht, committed]
"Gut. Milestone 2: Nur die API-Route für User-Liste"
[Agent macht, committed]
"Gut. Milestone 3: Nur die Frontend-Komponente"
[Agent macht, committed]
4. Eskalations-Strategien
Wenn Cursor hängt, brauchst du ein System. Nicht Panic, sondern Prozess.
Die 3-Stufen-Eskalation:
Stufe 1: Cursor fragen "Erkläre das Problem"
Bevor du eskalierst: Lass Cursor selbst erklären was das Problem ist.
Prompt:
"Erkläre mir unser aktuelles Problem so, dass ich es einem anderen Entwickler
erklären kann. Beschreibe:
1. IST-Zustand (was passiert gerade)
2. SOLL-Zustand (was sollte passieren)
3. Was wir versucht haben (welche Lösungsansätze)
4. Warum es nicht funktioniert (deine Theorie)"
Warum das wichtig ist:
• Cursor muss Problem strukturieren (hilft ihm selbst)
• Du bekommst Material für Eskalation
• Manchmal findet Cursor dabei selbst die Lösung
Stufe 2: Eskalation zu ChatGPT/Claude als "externer Dev"
Cursor's Erklärung mitnehmen und an frische KI geben.
Prompt-Template:

[Code-Block oder Projekt-Export]

Format der Lösung:
"Sag deinem Entwickler:

3. [Schritt 3]"
Stufe 3: Model-Switch (GPT-5 oder Opus 4.1)
Wenn ChatGPT/Claude auch nicht weiterhilft: Andere KI, andere Perspektive.
Wann Model-Switch:
• Problem ist sehr komplex (Architektur-Entscheidung)
• ChatGPT/Claude gibt unbefriedigende Antwort
• Du brauchst "zweite Meinung"
• Problem ist domain-spezifisch (z.B. ML, Crypto)
Prompt bleibt gleich, nur anderes Modell.
5. Git als Undo-Button & Experiment-Safety-Net
Git ist nicht nur Versionskontrolle. Es ist dein wichtigstes Safety-Tool.
Checkpoint-Strategie: Alle 5-10 Minuten
Warum so häufig?
• Agent kann in 5 Min viel kaputt machen
• Du willst granulare Rollback-Points
• Kleine Commits = einfaches Cherry-Picking später
• Du verstehst Code besser wenn Changes klein sind
Praktische Umsetzung:
Cursor macht automatisch Commits während Agent Mode. Aber du solltest
Commit-Messages kontrollieren.
Der sichere Git-Workflow:
Before Start:
git status # Clean State?
git log --oneline # Wo sind wir?
git checkout -b feature/xyz # Neuer Branch
During Agent Mode:
# Alle 5-10 Min (Agent macht automatisch, du schaust nur):
git log --oneline -5 # Was wurde committed?
git diff HEAD~1 # Was hat sich geändert?
When Problem:
# Option 1: Reject letzter Commit
git reset --soft HEAD~1 # Undo aber Changes bleiben
git reset --hard HEAD~1 # Undo und Changes weg
# Option 2: Reject mehrere Commits
git reset --hard HEAD~3 # Zurück zu 3 Commits vorher
# Option 3: Zurück zu bestimmtem Commit
git log --oneline # Finde guten Commit-Hash
git reset --hard abc123 # Zurück zu diesem Stand
After Feature Done:
# Cleanup Commits (optional)
git rebase -i HEAD~10 # Push to Remote
git push origin feature/xyz
# Create PR (außerhalb von Cursor)
# Squash kleine Commits
6. Review-Checklist nach Agent-Mode-Session
Nach jeder Agent-Mode-Session (oder alle 30 Min): Review. Nicht blind vertrauen.
Die Agent-Mode-Review-Checklist:
✅ Code-Qualität:
• Verstehe ich, was der Code macht?
• Sind Naming-Conventions eingehalten?
• Gibt es offensichtliche Code-Smells?
• Sind Error-Handling vorhanden?
• Sind Edge-Cases bedacht?
✅ Funktionalität:
• Funktioniert das Feature wie gewünscht?
• Habe ich lokal getestet?
• Was passiert bei Invalid Input?
• Was passiert bei Network-Errors?
• Gibt es Performance-Probleme?
✅ Security:
• Keine Secrets hardcoded?
• Input-Validation vorhanden?
• SQL-Injection-safe?
• XSS-Protection?
• Authentication/Authorization korrekt?
✅ Git-History:
• Sind Commit-Messages aussagekräftig?
• Kann ich die Changes nachvollziehen?
• Gibt es sinnvolle Breakpoints für Rollback?
• Ist Branch clean (keine merge-conflicts)?
✅ Dokumentation:
• Sind neue Features dokumentiert?
• Sind Breaking-Changes dokumentiert?
• Ist README aktuell?
• Sind API-Docs aktualisiert?
🚩 Red Flags - Sofort Action nötig:
• 🚩 Code den du nicht verstehst (dann kannst du ihn auch nicht debuggen)
• 🚩 Hunderte Zeilen in einem Commit (zu viel auf einmal)
• 🚩 Dependencies die du nicht kennst (warum wurde X installiert?)
• 🚩 Gelöschte Files ohne Rückfrage (wo ist X hin?)
• 🚩 Production-URLs im Code (sollten in .env sein)
• 🚩 console.log überall (Debug-Code nicht aufgeräumt)
• 🚩 Commented-Out-Code (warum nicht gelöscht?)
• 🚩 TODO-Comments ohne Issue-Nummer (werden vergessen)
Zusammenfassung: Safety-First-Mindset
Die wichtigsten Takeaways:
• 30-Minuten-Regel: Niemals länger unbeaufsichtigt, Review alle 30 Min
• 5 Safeguards: DELETE, PUSH, DEPLOY, BREAKING, SECRETS - alle geschützt
• Loop-Detection: 4 Loop-Typen kennen, früh erkennen, schnell eskalieren
• 3-Stufen-Eskalation: Cursor fragen → ChatGPT/Claude → Model-Switch
• Git als Safety-Net: Commits alle 5-10 Min, granulare Rollback-Points
• Review-Checklist: Nach jeder Session: Code, Funktionalität, Security, Git, Docs
Final Wisdom:
Agent Mode ist kein Autopilot. Es ist ein Co-Pilot. Du bist immer der Pilot.
Immer.
Die besten Entwickler mit KI sind nicht die, die der KI blind vertrauen. Es sind die, die
wissen wann sie vertrauen können und wann sie eingreifen müssen.

TEIL V: KORREKTUR-PULSE & DEBUGGING
Wenn der Code nicht macht, was er soll
Debugging mit KI ist anders als klassisches Debugging.
Du bist nicht mehr der Einzige, der den Fehler suchen muss. Aber du musst
entscheiden: Welcher Fehler ist relevant? Wann eskalierst du? Wann rollst du
zurück?
Dieses Kapitel zeigt dir den kompletten Debug-Workflow - von der ersten
Fehlermeldung bis zur Lösung.
1. Der erste Fehler: Verstehen vor Handeln
Die meisten Entwickler machen einen Fehler: Sie sehen einen Error und geben ihn
sofort an die KI.
Das Problem: Nicht jeder Error ist für das Problem verantwortlich. Manchmal sind
es Side-Effects, manchmal ist der eigentliche Error woanders.
Der 3-Schritt-Debug-Workflow:
Schritt 1: Error selbst lesen und validieren
Frage dich:
• Ist dieser Error für mein aktuelles Problem verantwortlich?
• Oder ist das ein alter Error, der schon vorher da war?
• Gibt es mehrere Errors - welcher ist der primäre?
• Was passiert genau, wenn der Error auftritt?
Praktisches Beispiel:
User kann sich nicht einloggen. Im Terminal: 5 verschiedene Warnings + 1 Error.
Lies alle 6 Messages. Oft ist nur der Error relevant, die Warnings sind Noise.
Schritt 2: Error + Kontext an KI übergeben
Erst wenn du sicher bist, dass der Error relevant ist:
Beispiel-Prompt:
IST: User klickt auf "Login", Form wird submitted, aber nichts passiert
ERROR (siehe Screenshot): "Cannot read property 'token' of undefined"
SOLL: Nach Login soll User zum Dashboard redirected werden
Context: Login-Form sendet POST zu /api/auth/login, Backend gibt Token zurück,
Frontend soll Token in localStorage speichern.
Fix bitte und erkläre, was das Problem war.
Schritt 3: KI-Lösung validieren
Cursor macht einen Fix. Jetzt musst du prüfen:
• Ist der Error weg? (Nicht nur "Cursor sagt es ist weg")
• Funktioniert das Feature jetzt wirklich?
• Hat der Fix andere Dinge kaputt gemacht?
• Verstehst du, was Cursor geändert hat?
⚠ Wichtig: Wenn Cursor sagt "Ich hab's gefixt" aber der Error kommt wieder - das
ist der erste Indikator für einen Loop (siehe nächster Abschnitt).
2. Loop Detection: Wann die KI im Kreis läuft
Die gefährlichste Situation: Cursor "fixt" denselben Fehler wieder und wieder, aber
nichts wird besser.
Aus der Praxis: Wenn Cursor 2-3x behauptet, etwas gefixt zu haben, aber der Error
bleibt - das ist ein Loop.
Die 4 häufigsten Loop-Typen:
Loop-Typ 1: "Ist gefixt" aber offensichtlich nicht
Symptome:
• Cursor: "Error ist behoben, teste bitte"
• Du testest: Error ist noch da
• Cursor: "Ah sorry, jetzt habe ich es gefixt"
• Du testest: Immer noch da
• Repeat 2-3x
Action:
Nach 2-3 Versuchen: STOP.
1. Reject die letzten 2-3 Edits
2. Frage Cursor: "Erkläre mir das Problem so, dass ich es einem anderen Dev
erklären kann"
3. Diese Erklärung + Original-Error an ChatGPT/Claude eskalieren
Loop-Typ 2: Immer dieselbe Datei geändert
Symptome:
• Cursor editiert immer nur component.tsx
• Error ist aber vermutlich im Backend
• Oder: Cursor ändert immer nur CSS, Problem ist aber in der Logik
Action:
Wenn Cursor 3x dieselbe Datei ändert, aber Problem bleibt:
"Das Problem ist nicht in [Datei]. Schau dir [andere Bereiche] an: [Backend/State
Management/API/etc.]"
Loop-Typ 3: Macht eigene Fixes rückgängig
Symptome:
• Cursor ändert Zeile 45 von A zu B
• Nächster Edit: Zeile 45 wieder von B zu A
• Übernächster Edit: Zeile 45 wieder von A zu B
• Cursor ist sich selbst unsicher
Action:
Sofort stoppen. Das ist Unsicherheit, keine echte Debugging-Strategie.
Eskalieren zu ChatGPT/Claude mit Frage: "Was ist der richtige Ansatz hier?"
Loop-Typ 4: Zu viele Änderungen, nichts funktioniert mehr
Symptome:
• Cursor hat 10+ Dateien geändert
• Ursprünglicher Error ist weg
• Aber jetzt gibt es 5 neue Errors
• Du verlierst den Überblick, was überhaupt noch funktioniert
Action:
ROLLBACK. Zurück zum letzten funktionierenden Stand (Git).
Dann: Neu anfangen, aber diesmal Schritt für Schritt mit Checkpoints.

Wenn etwas kaputt geht, hast du 2 Optionen:

Die 50/50-Regel aus der Praxis:
50% der Fälle: Forward Patch (kleine Probleme, klar eingegrenzt)
50% der Fälle: Rollback (datei-übergreifend, unübersichtlich)
Entscheidungskriterium: Übersichtlichkeit. Sobald du nicht mehr genau siehst, was
wo geändert wurde = Reject.
Praktische Entscheidungshilfe:
✅ Forward Patch wenn:
• Nur 1-2 Dateien betroffen
• Du verstehst jeden Edit
• Problem ist klar lokalisierbar
• Änderungen sind klein (<20 Zeilen pro Datei)
🔄 Rollback wenn:
• 5+ Dateien geändert
• Du scrollst durch Diffs und verstehst es nicht mehr
• Neue Errors tauchen auf
• Du denkst "Was hat Cursor da eigentlich gemacht?"
4. Eskalation: Wann ChatGPT/Claude als "Zweite
Meinung"
Cursor ist dein primäres Build-Tool. Aber manchmal hängt Cursor fest - dann
brauchst du eine zweite Perspektive.
Die 3-Stufen-Eskalation:
Stufe 1: Cursor alleine (80% der Fälle)
Wann:
Klare Aufgaben, Standard-Features, keine unerwarteten Probleme
Vorgehen:
• IST/SOLL-Prompts
• Agent Mode unter Aufsicht
• Iterative Entwicklung
• Git-Checkpoints alle 5-10 Min
Stufe 2: ChatGPT/Claude als Berater (15% der Fälle)
Trigger:
• Cursor hängt in Loop (2-3 Versuche)
• Cursor versteht dein Problem nicht
• Du verstehst Cursors Lösung nicht
• Architektur-Entscheidung nötig
Vorgehen:
1. Cursor fragen: "Erkläre mir unser Problem so, dass ich es einem anderen Dev
erklären kann"
2. Diese Erklärung + Code (optional: Export-Script) an ChatGPT/Claude
3. ChatGPT/Claude gibt Lösung "für deinen Entwickler"
4. Diese Lösung zurück an Cursor mit Anweisung
Beispiel-Eskalations-Prompt:
Mein Entwickler (Cursor) hängt bei folgendem Problem:
[Cursor's Erklärung hier einfügen]
Code-Context: [Optional: Export von relevantem Code]
Gib mir eine Lösung, die ich meinem Entwickler als Anweisung geben kann.
Stufe 3: Model-Wechsel (5% der Fälle)
Trigger:
• ChatGPT/Claude kommt auch nicht weiter
• Extrem komplexes Problem
• Braucht spezialisiertes Model (z.B. GPT-5 für Math, Opus 4.1 für Reasoning)
Vorgehen:
Wechsel zwischen Claude Sonnet 4.5 → GPT-5 → Opus 4.1
Je nach Stärke des Models für deine spezifische Aufgabe
5. Max Mode: Security & Quality-Review
Nach größeren Features: Lass die KI nochmal über alles drüberschauen.
Max Mode = Großes Context-Window, Projekt-weite Analyse
Wann Max Mode nutzen?
• Nach Completion eines größeren Features
• Vor Deployment to Production
• Nach vielen schnellen Iterationen
• Wenn du "blind" viel geändert hast
Der Max-Mode-Review-Prompt:
Scanne das gesamte Projekt und prüfe auf:
1. Security-Probleme:
• Ungeschützte API-Endpoints
• Fehlende Input-Validation
• SQL -Injection-Risiken
• XSS-Vulnerabilities
2. Datenschutz-Issues:
• Sensitive Daten in Logs
• Credentials im Code
• Fehlende Encryption
3. Code-Quality:
• Duplikate
• Tote Code-Pfade
• Performance-Bottlenecks
Gib mir eine priorisierte Liste: Critical, High, Medium, Low
Best Practice: Max Mode Review alle 2-3 Tage oder nach jedem größeren Feature.
Nicht erst vor Production - dann ist es zu spät für große Fixes.
6. Reject-Strategie: Trash-Code vermeiden
Nicht jeder Edit von Cursor ist gut. Manchmal baut Cursor Workarounds, die
technische Schulden erzeugen.
Die Reject-Funktion in Composer ist dein Freund.
Wann rejecten?
Code funktioniert, aber ist "hacky"
Cursor hat einen Workaround gebaut, der zwar läuft, aber du siehst schon: Das wird
später Probleme machen.
Zu viele Änderungen auf einmal
Cursor hat 8 Dateien geändert. Du verstehst nicht mehr, was zusammenhängt.
Code ist unleserlich
Funktioniert, aber kein Mensch kann das in 2 Wochen noch verstehen.
Verletzt Best Practices
z.B. alle Logik in einer 500-Zeilen-Funktion, keine Separation of Concerns
Der richtige Reject-Workflow:
1. Reject im Composer
2. Prompt: "Das funktioniert, aber [Problem beschreiben]. Bau das sauberer:
[Erwartung beschreiben]"
3. Cursor macht neuen Versuch
4. Wenn wieder nicht gut: Eskaliere zu ChatGPT/Claude für Architektur-Input
⚠ Wichtig: Reject ist kein "Undo". Es verwirft nur den letzten Vorschlag von Cursor.
Für echtes Undo brauchst du Git-Rollback.
7. Error-Log-Dokumentation: Aus Fehlern lernen
Jeder Bug ist eine Lern-Gelegenheit. Aber nur, wenn du ihn dokumentierst.
Aus der Praxis: Die KI kann Fehler dokumentieren, du musst nur das System
aufsetzen.
Das Debug-Log-System:
Struktur:
/docs/ Ordner im Projekt-Root
Dateinamen: debug_YYYY-MM-DD_kurze-beschreibung.md
KI schreibt die Logs, du reviewst sie
Was gehört in ein Debug-Log?
• Problem-Beschreibung (Was sollte funktionieren, tut es aber nicht?)
• Error-Message (Vollständig, mit Stack Trace)
• Was versucht wurde (Welche Fixes haben nicht funktioniert?)
• Was funktioniert hat (Die finale Lösung)
• Root Cause (Warum trat das Problem auf?)
• Prevention (Wie verhindern wir das in Zukunft?)
Beispiel-Prompt für Debug-Log:
Dokumentiere diesen Bug in /docs/debug_2025-11-12_login-token.md:
• Problem: User konnte sich nicht einloggen
• Error: "Cannot read property 'token' of undefined"
• Was nicht funktioniert hat: [Liste]
• Was funktioniert hat: [Lösung]
• Root Cause: [Warum?]
• Prevention: [Wie verhindern?]
Von Debug-Log zu .cursorrules:
Das selbstlernende System:
1. Bug tritt auf → Debug-Log wird geschrieben
2. Tritt derselbe Bug-Typ nochmal auf? → Pattern erkannt
3. Pattern-Erkenntnis geht in .cursorrules
4. Cursor macht denselben Fehler nicht mehr
Beispiel:
Bug: Cursor deployt auf Remote statt lokal zu testen
→ Debug-Log dokumentiert das Problem
→ Passiert 2x
→ In .cursorrules: "Nie mit cp auf Remote deployen. Immer erst lokal testen."

TEIL VI: PARALLEL-WORK & ENERGY-
MANAGEMENT
Die Kunst des Mehrprojekt-Managements
Mit Agent Mode kannst du mehrere Projekte parallel bearbeiten.
Das klingt gut. Aber: Es ist auch die Hauptquelle von Erschöpfung.
In diesem Kapitel: Wie du 2-3 Projekte gleichzeitig managst, ohne auszubrennen.
Was dich wirklich ermüdet (Spoiler: nicht das Coding). Und wie du deinen Workflow
so strukturierst, dass du produktiv bleibst.
1. Die 3-Projekte-Rotation: Wie es funktioniert
Das Setup:
Du hast 3 Projekte gleichzeitig offen. Jedes in eigenem Cursor-Window. Während
Agent Mode in Projekt 1 arbeitet, kontrollierst du Projekt 2, stößt Agent in Projekt 3
an, dann zurück zu Projekt 1.
Das ist 3x Output in der gleichen Zeit. Aber auch 3x kognitive Last.
Der Rotations-Workflow:
Schritt-für-Schritt:
1. Projekt 1: Agent starten
Agent Mode in Composer aktivieren, Feature-Auftrag geben, Agent läuft
los. Erwartete Dauer: 15-30 Minuten.
2. Wechsel zu Projekt 2
Während Projekt 1 Agent arbeitet: Projekt 2 öffnen, prüfen was Agent
gebaut hat, testen, nächsten Schritt prompten, Agent in Projekt 2 starten.
3. Wechsel zu Projekt 3
Projekt 2 Agent läuft jetzt. Zu Projekt 3 wechseln, Status checken, Probleme
sichten, Agent anstoßen.
4. Zurück zu Projekt 1
Projekt 3 Agent läuft. Zurück zu Projekt 1: Agent sollte fertig sein. Review,
nächster Schritt, Agent neu starten.
5. Repeat
1 → 2 → 3 → 1 → 2 → 3 → ...

-
Feature)

⚡ Die Realität: In 45 Minuten hast du 3 Projekte vorangebracht. Jedes Projekt hat
15-20 Minuten Agent-Zeit bekommen, aber du warst nie untätig.
Das Geheimnis: Während ein Agent arbeitet, arbeitest du am nächsten.
2. Was dich wirklich ermüdet: Context-Switching
Die größte Fehleinschätzung: "Ich bin müde, weil ich so viel gecoded habe."
Falsch. Du bist müde, weil du ständig zwischen Projekten wechselst.
Das Context-Switching-Problem:
Was passiert bei jedem Projekt-Wechsel:
• Mental Model neu laden ("Wo waren wir? Was war das Problem?")
• Stack verstehen (Backend? Frontend? Welche APIs? Welcher State?)
• Kontext aus Git-History/Docs rekonstruieren
• Agent-Status einschätzen ("Was hat der Agent gebaut? Ist es gut?")
• Nächste Schritte planen ("Was kommt als nächstes?")
Die versteckte Rechnung:
• Pro Projekt-Wechsel: ~3-5 Minuten Context-Loading
• 3 Projekte = 6 Wechsel pro Stunde (1→2→3→1→2→3)
• 6 × 4 Minuten = 24 Minuten/Stunde nur für Context-Switching
40% deiner Zeit geht für "Wo war ich nochmal?" drauf.
Vergleich: 1 Projekt vs. 3 Projekte
Faktor 1 Projekt (8h Tag) 3 Projekte (8h Tag)
Reine Arbeitszeit ~7h (1h Pausen) ~5h (3h Context-
Switching)
Output 1 Feature komplett 3 Features zu 60-70%
Mentale Last Niedrig (ein Kontext) Hoch (drei Kontexte)
Erschöpfung Normal Deutlich höher
Das Produktivitäts-Paradox:
• 3 Projekte = 3x Output (stimmt)
• Aber: 3x Erschöpfung (stimmt auch)
• Nicht das Coding ermüdet, sondern das Switching
Du bist nicht müde vom Arbeiten. Du bist müde vom Umschalten.
3. Die 2-Projekte-Maximum-Regel
Nach 1 Jahr Erfahrung mit Parallel-Work: Die meisten sollten bei max. 2 Projekten
bleiben.
Empfehlung aus der Praxis:
• Standard: 1 Projekt (Deep Work)
• Bei Agent-Wartezeiten: 2 Projekte (produktiv)
• Nur in Ausnahmefällen: 3 Projekte (Deadline-Druck)
2 Projekte = der Sweet Spot zwischen Produktivität und Nachhaltigkeit.
Zusammenfassung: Parallel-Work Cheat-Sheet
Das komplette Parallel-Work-Framework:
• Rotation: 1→2→3→1 - Während Agent in Projekt 1 läuft, arbeitest du an Projekt 2
• Was ermüdet: Context-Switching - Nicht das Coding, sondern das mentale
Umschalten
• Sweet Spot: 2 Projekte - Produktiv, aber nachhaltig. 3 nur bei Deadline-Druck.
• Energy: Begrenzte Ressource - Nach 3-Projekt-Tag brauchst du Recovery
🎯 Kern-Erkenntnis: Parallel-Work mit Agent Mode macht dich 2-3x produktiver.
Aber es ist kein Freibrief für endloses Arbeiten. Energy-Management ist genauso
wichtig wie Code-Management.

Vom Wissen zur Praxis

Übung 2: Debug-Loop & Eskalation
Dauer: 40 Minuten | Schwierigkeit: Mittel
Lernziel
Was du lernst:
• Loops erkennen (2-3 Versuche = Loop)
• Eskalations-Workflow verstehen
• Cursor als "Entwickler" behandeln, ChatGPT/Claude als "Berater"
• "Nicht mein Weg" loslassen
Aufgabe
Fixe absichtlich kaputten Code mit 3 verschiedenen Bug-Typen
Du bekommst ein Projekt mit 3 Bugs:
1. Offensichtlicher Fehler (Typo)
2. Loop-Kandidat (Race Condition)
3. Architektur-Problem (State Management)
Setup: Code-Repo mit Bugs
Erstelle ein simples React-Projekt mit diesen Bugs:
Bug 1 - Typo (leicht):
```javascript
const [userName, setUserName] = useState('');
// Später im Code:
console.log(usrName); // Typo: usrName statt userName
```
Bug 2 - Race Condition (Loop-Kandidat):
```javascript
useEffect(() => {
fetchData();
setData(response); // setData direkt, keine async/await
}, []);
```
Bug 3 - State-Problem (schwer):
```javascript
// Parent übergibt State an Child, aber Child ändert State direkt
<ChildComponent data={parentData} onChange={setParentData} />
// Child macht: props.data.value = newValue (statt onChange)
```
Phase 1: Bug 1 fixen (5 Min)
Cursor Prompt:
IST: Console zeigt "usrName is not defined"
SOLL: userName soll geloggt werden
Fix bitte
Erwartung: Cursor fixt das sofort (1 Versuch). Easy win.
Phase 2: Bug 2 angehen (15 Min)
Cursor Prompt:
IST: fetchData wird aufgerufen, aber data bleibt undefined
ERROR: Cannot read property of undefined
SOLL: Data soll nach fetch gesetzt werden
Fix bitte.
Beobachte: Cursor wird vermutlich 2-3 Versuche brauchen. Er wird sagen "gefixt",
aber es funktioniert nicht. Das ist deine Loop-Erfahrung.
Nach 3. Versuch: ESKALIEREN
1. Cursor fragen: "Erkläre mir unser Problem so, dass ich es einem anderen Dev
erklären kann"
2. Diese Erklärung + Code an ChatGPT/Claude: "Mein Entwickler hängt hier..."
3. Lösung von ChatGPT/Claude zurück an Cursor
Phase 3: Bug 3 - Das schwere Problem (15 Min)
Cursor Prompt:
IST: Child-Component ändert data direkt, Parent sieht Änderungen nicht
SOLL: Änderungen sollen im Parent ankommen
Fix bitte.
Beobachte: Cursor wird vermutlich einen anderen Ansatz vorschlagen als du
erwartet hast. Vielleicht Context API statt Props, oder useReducer.
Deine Aufgabe: Akzeptieren. Auch wenn es nicht dein Weg ist - wenn es
funktioniert, ist es gut.
Phase 4: Dokumentation (5 Min)
Cursor Prompt:
Dokumentiere alle 3 Bugs in /docs/debug_2025-11-12_exercise.md:
• Was war das Problem?
• Was haben wir versucht?
• Was hat funktioniert?
• Learnings für .cursorrules
Success-Kriterium
Du hast die Übung verstanden, wenn:
• Du eine Loop erkannt hast (Bug 2)
• Du eskaliert hast zu ChatGPT/Claude
• Du einen unerwarteten Lösungsweg akzeptiert hast (Bug 3)
• Alle 3 Bugs sind gefixt und dokumentiert

3. .cursorrules Templates
Basis-Template (für jedes Projekt):
# Projekt-Rules für [Projektname]
## Safety First
- NIEMALS DELETE ohne explizite Nachfrage
- NIEMALS GIT PUSH ohne Confirmation
- IMMER erst lokal testen, dann deployen
## Code-Style
- Sprache: [Deutsch/Englisch] für Variablen & Kommentare
- Kommentare: Nur wenn nötig, Code soll selbsterklärend sein
- Naming: camelCase für JS/TS, snake_case für Python
## Testing
- Jede neue Function: Test mit Edge-Cases
- Vor jedem Commit: Tests laufen lassen
## Git-Workflow
- Commits: Ausführlich auf Englisch
- Format: "type: description" (feat, fix, docs, refactor)
- Branches: feature/xyz, bugfix/xyz, hotfix/xyz
## Dokumentation
- README aktuell halten
- API-Änderungen dokumentieren
- Komplexe Logik: Inline-Kommentare
Erweitert: Privacy-First-Projekt
# Privacy-Rules (zusätzlich zu Basis-Rules)
## Data Handling
- KEINE Sensitive Daten in Logs
- KEINE Credentials im Code (nur Env-Variables)
- Alle User-Daten: Verschlüsselt speichern
## DSGVO-Compliance
- User-Consent vor Daten-Collection
- Delete-Funktion für User-Daten implementieren
- Daten-Export-Funktion bereitstellen
## Testing mit Sensitive Data
- NUR Mock-Daten in Tests
- Echte User-Daten: Lokal anonymisieren
Erweitert: Team-Projekt
# Team-Rules (zusätzlich zu Basis-Rules)
## Code-Review
- Kein direkter Push auf main
- Pull Requests: Mindestens 1 Reviewer
- PR-Description: Was, Warum, Test-Anweisungen
## Kommunikation
- Breaking Changes: Slack-Message an Team
- Große Refactors: Vorher absprechen
- Neue Dependencies: Erst diskutieren
## Onboarding
- README für neue Devs aktuell halten
- Setup-Script bereitstellen
- Architektur-Diagramm pflegen
4. Success-Metriken: Bist du auf dem richtigen Weg?
Woran merkst du, dass Vibe Coding für dich funktioniert?
Technische Metriken:
Features pro Woche
Baseline etablieren: Wie viele Features schaffst du jetzt?
Ziel: 2-3x mehr als vorher (nach 1-2 Monaten Übung)
Code-Quality
Kannst du den Code, den KI schreibt, verstehen?
Ziel: 90%+ des Codes ist nachvollziehbar, 0% "Magic"
Bug-Rate
Wie viele Bugs pro Feature?
Ziel: Gleich oder niedriger als bei manuellem Coding
Refactoring-Bedarf
Wie oft musst du KI-Code später umschreiben?
Ziel: <20% des Codes braucht später Refactoring
Prozess-Metriken:
Loop-Frequency
Wie oft hängt Cursor in Loops?
Ziel: <1 Loop pro Tag (nach 2 Monaten)
Eskalations-Rate
Wie oft eskalierst du zu ChatGPT/Claude?
Ziel: 10-20% der Tasks (mehr ist OK bei komplexen Problemen)
Time-to-First-Code
Vom Prompt zum ersten funktionierenden Code?
Ziel: <15 Min für einfache Features, <60 Min für komplexe
Git-Commit-Frequency
Wie oft commitest du?
Ziel: Alle 5-15 Min (Checkpoints funktionieren)
Subjektive Metriken (wichtig!):
Verstehst du deinen Code?
Kannst du erklären, was jede Datei macht?
Red Flag: "Keine Ahnung, KI hat das gebaut"
Fühlst du dich produktiv?
Oder fühlst du dich wie ein Copy-Paste-Bot?
Ziel: Du orchestrierst, KI führt aus
Lernst du noch?
Siehst du neue Patterns, Ansätze?
Red Flag: "Ich mach nur noch, was KI sagt"
Kannst du ohne KI?
Wenn Cursor ausfällt - kannst du weiterarbeiten?
Ziel: Ja, nur langsamer
5. Red Flags: Wann läuft es schief?
Warnsignale, dass du vom Weg abkommst:
🚩 "Ich versteh den Code nicht mehr"
Problem: Du lässt Agent zu lange alleine, ohne mitzudenken
Lösung: Kleinere Agent-Tasks, mehr Checkpoints, jeden Edit verstehen
🚩 "Ich kopiere nur noch, was KI sagt"
Problem: Du bist passiv geworden
Lösung: Mehr in Konzept-Phase investieren, KI challengen
🚩 "Alles wird immer langsamer"
Problem: Tech-Debt häuft sich, Code wird schlechter
Lösung: Max Mode Reviews, mehr Reject bei schlechtem Code
🚩 "Ich kann nichts mehr ohne KI"
Problem: Skills verkümmern
Lösung: 1 Tag/Woche ohne Agent Mode, nur manuelle Arbeit
🚩 "Agent macht ständig dasselbe falsch"
Problem: .cursorrules nicht aktuell/nicht genutzt
Lösung: Learnings in .cursorrules dokumentieren
🚩 "Ich bin komplett ausgebrannt"
Problem: Zu viel Parallel-Work, keine Pausen
Lösung: Zurück zu 1-2 Projekten, Energy-Management ernst nehmen

Schlusswort
Produktives Vibe Coding ersetzt kein Können. Es multipliziert es.
Architektur-Entscheidungen, Debugging, das Verständnis für den eigenen Code -
das bleibt bei dir. Was wegfällt: Stunden mit Boilerplate, Kämpfe gegen Syntax-
Fehler, das manuelle Tippen von allem.
Die KI ist ein Werkzeug. Ein mächtiges. Aber du bleibst der Entwickler.
PULSE gibt dir die Struktur dafür. Der Loop läuft, du setzt die Impulse an den
richtigen Stellen. Kontrollierte Entwicklung statt blindem Vertrauen.
Ein Hinweis zu den Modellen: Claude Sonnet 4.5, GPT-5 und Opus 4.1 sind Stand
November 2025 die leistungsfähigsten. Das ändert sich. Die Prinzipien in diesem
Framework bleiben - die Tools passen sich an.
